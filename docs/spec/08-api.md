## API

One JSON API over HTTPS serves every screen. Every write is safe to retry, every change is audited, and live events tell screens what to fetch again.

**Conventions**

- **Paths** are scoped by venue: `/v1/venues/{venueId}/…`. The API checks the caller's membership, then sets the venue for the row-level policy. Guest routes live under `/v1/public/…` and take a venue slug, a signed token or a room-session cookie.
- **Principals.** Every route declares which principals may call it ([Tenancy and access](02-tenancy-access.md)), and any other caller gets `403`. Staff routes also check the caller's role (owner, manager, bartender, front_desk or staff) against `role_permissions`.
- **Sign-in.** Owners and managers use a session cookie on the web and a bearer token in the desktop app. There are no passwords: the email names the account, and the proof is a passkey (user verification required) or an authenticator-app code sent together with a one-time code emailed first. Every session records how it was opened (`passkey`, `authenticator`, `pin` or `badge`), lasts 12 hours and locks after 30 idle minutes (`401 session_locked`; `401 session_expired` once it's over). Staff get a short session from the device's signature plus a badge tap or their name and PIN, ended when the device locks or someone else's badge takes over. A PIN session never reaches settings, team changes or exports, even for a manager; those, and deciding approvals, need the passkey session (`403 forbidden`, "Admin needs a passkey"; an authenticator session is refused the same way). Large refunds, exports, team changes and card-fee changes ask for the passkey again: the write carries an `X-Step-Up` token from `POST /v1/auth/step-up`, good once and for five minutes, or answers `403 step_up_required`. Guests use a token scoped to one booking or one room session.
- **Approvals.** A write that needs approval (a comp or void over the reason-only limit, a refund, a clock pause, a tip over the review limit, a paid-out over the limit, a lower party size after gratuity, a card-on-file charge without the guest, an order over a declined hold) doesn't fail. It answers `202 approval_pending` with the approval and who it's waiting for ("Waiting for Andy"), the screen keeps working, and the change is made when the approver approves it on their own phone. `approval.decided` tells the requester's screen.
- **Training mode.** A caller in training mode, by person or by device, gets practice checks numbered T-0012 and so on. Their card payments go to a simulated reader on Stripe's sandbox, never live Stripe, and nothing they do reaches totals, tips or exports.
- **Idempotency.** Every POST and PATCH takes an `Idempotency-Key`, required on money routes. The server stores the key before doing the work, with the venue, the caller and a hash of the request. A duplicate that arrives while the first is running gets `409 in_progress`, the same key with a different body gets `422 key_reused`, and a finished request replays its answer for 7 days.
- **Money and time.** Amounts in integer cents with `currency: "usd"`; times in ISO 8601 with an offset. Every response, and every WebSocket hello, carries `server_time`.
- **Conflicts.** Checks carry `version`; edits send `If-Match` and get `409` if someone else changed the check first.
- **Clients.** Every response carries `min_client_version`. An older staff or desktop app keeps working and updates between business days.
- **Errors.** `{ "error": { "code": "hold_declined", "message": "…", "retryable": false } }`. The codes screens branch on: `module_off` (404), `forbidden` (403), `version_conflict` (409), `in_progress` (409), `alcohol_closed` (409), `cut_off` (409), `ordering_closed` (409, the check is presented), `orders_open` (409, an order is still ringing or held), `room_not_free` (409, the room doesn't fit or isn't free for the time needed), `over_amount_due` (422), `over_refundable` (422, more than the payment captured minus earlier refunds), `key_reused` (422), `approval_pending` (202), `payment_unknown` (202), `reader_busy` (409), `reader_offline` (503), `session_locked` (401), `session_expired` (401) and `step_up_required` (403).
- **Lists** page with a cursor (`?after=`) and at most 100 items per page, and filter with `?status=` or `?state=` where the table has one. Reports run on a read replica with a 5-second limit.

**Live events.** Every change writes a `venue_events` row in the same transaction. One relay, the leader under an advisory lock, reads committed rows in commit order and stamps `seq`. Every API container then tails `venue_events` by `seq`, woken by NOTIFY on its own connection and polling each second as a backstop, and pushes to its own WebSockets. A screen opens one WebSocket, filtered to what its principal may see, so a room tablet gets only its room's channel. Each event is small, `{ "seq": 1042, "type": "order.ringing", "id": "…", "entity_version": 7, "at": "…" }`, and the screen fetches the resource again; events never carry the money math. A screen that reconnects sends the last `seq` it saw and gets everything after it (events are kept 72 hours). A gap means a full refetch, and `entity_version` lets a screen ignore a stale read. Refetches are grouped for 250 ms, reconnects back off with jitter, and deploys drain sockets slowly.
